## 0. 结论摘要

**「统一 AI 模型中台」的数据层与管理面已经建成，但运行面（真正跑用户流量的那条链路）完全没有接入。**

`019_unified_ai_routing_and_pricing.sql` 的 9 张新表已在线上的 PostgreSQL 中创建并有种子数据，`smartRouter` / `pricingEngine` / `circuitBreaker` / 9 个 `ProviderAdapter` / `attempts` / `costRecords` 仓储均已提交入库——**但没有任何一条生产调用链引用它们**。

三条硬证据：

1. `routeGenerationTask`（智能路由入口）全仓只有一个探针脚本 `scripts/probes/_probe_adapters.mjs:13` 引用，生产代码零引用。
2. `ai_studio.generation_attempts`、`route_decision_logs`、`provider_cost_records` 三张表线上行数均为 **0**；`generation_quotes` 仅 **3** 行（手工测试痕迹）。
3. `verifyAndConsumeQuote`（报价防篡改校验）全仓零调用；报价接口只写不用。

更关键的是：**Studio 前端的生成请求根本不经过平台生成 API**，而是走一条把平台自己的 MuAPI 密钥直接代理给 `api.muapi.ai` 的透传通道。因此积分、路由、成本核算对真实用户流量全部不可见。这既是本次改造的核心目标，也是当前最严重的资金敞口。

## 3. 运行链路现状：三套供应商抽象并存

| 抽象 | 位置 | 是否承载生产流量 |
|---|---|---|
| 旧「万能 HTTP provider」 | `lib/services/generationProviders.js` | **是**（被 `generationCore` 使用） |
| 新 Adapter 体系 | `lib/adapters/*` | 否（仅后台渠道测试 + 健康探针） |
| 透传代理 | `app/api/api/v1/[[...path]]/route.js` | **是**（承载全部 Studio 真实生成流量） |

### 3.1 【P0 资金敞口】透传代理绕过计费与风控

`app/api/api/v1/[[...path]]/route.js:83-85`：任意登录用户 `POST /api/api/v1/<任意路径>`，服务端即以**平台自有 MuAPI 密钥**转发至 `api.muapi.ai`，路径与请求体原样透传。

已确认该密钥真实存在（`ops_bill.provider_secrets` 有 `muapi / api_key`），故当前可利用。后果：

- **零计费**：不建 job、不预扣积分、不写 ledger、不计成本。任何注册用户可无限消耗平台余额。
- **路径不白名单**：`GET /api/api/v1/account/balance` 可把**平台账户余额**读给普通用户（Studio 自己就在轮询这个接口，只是没渲染）。
- **绕过内容审核**：`validatePromptSafety` 只挂在 `/api/generations`（`app/api/generations/route.js:36`）。
- **绕过限流**：该路由只有 `guardMutation` 体积限制，无 `consumeRateLimit`。
- 前端 `muapi_key`（`components/StandaloneShell.js:347`，localStorage + cookie）是上游开源项目的 BYOK 遗留物；代理**丢弃**客户端密钥改用服务端密钥（`cleanHeaders` 删 `x-api-key` 再 set）。也就是说 UI 在向用户暗示「用你自己的 key」，实际平台在付钱。

> 这一项不属于原始需求清单，但它是「真正打通计费」的前置条件。**只要这条通道存在，任何积分/路由/成本改造都不成立。** 建议作为 Phase 02 之前的 Phase 01.5 立即收敛。

### 3.2 旧 provider 内含被禁止的供应商分支与危险回落

`generationProviders.js` 在 service 层写满了供应商判断，违反设计原则 §7：

- `:43` `if (activeProvider === 'dashscope' || 'alibaba')` → 内联 `executeDashScopeGeneration`
- `:55` `if (isVolcengineProvider || isSeedreamModel)` → 内联 `executeVolcengineGeneration`（含 Seedream 版本号字符串嗅探、像素升规、`ModelNotOpen` 降级兜底）
- **`:37-40` 危险回落**：目标供应商无密钥时，静默改用 **MuAPI 的 key** 并把请求发给 **MuAPI 的 URL 与报文格式**。供应商 A 的失败会被记成 MuAPI 的成功或失败，成本归因与熔断统计同时失真。

而 `lib/adapters/index.js:53-56` 的注释明确写着这条铁律（"Never swap a MuAPI key onto a vendor adapter"），并且已经实现了 fail-closed——**可惜没人调用它**。新体系里 `KlingAdapter` / `RunwayAdapter` / `LumaAdapter` 等已经写完，反而不如旧路径覆盖的供应商多。

### 3.3 双熔断器，且持久化的那个一调用就报错

- **内存版**（`lib/services/providerRuntime.js:3` `const circuits = new Map()`）：在跑，但进程本地、重启即清零、不入库、不参与路由决策。
- **数据库版**（`lib/services/circuitBreaker.js`）：`recordProviderSuccess` / `recordProviderFailure` / `checkAndHalfOpenProvider` **零调用方**，完全休眠。

并且它有一个真实缺陷：

> `circuitBreaker.js:51` 写入 `circuit_state = 'open'`，而线上约束是
> `CHECK (circuit_state IN ('closed','circuit_open','half_open'))`（已实测确认）。
> 即 `recordProviderFailure` 一旦被接入就会抛 23514 约束冲突。

阈值也不一致：`circuitBreaker.js:7` 默认 5，`aiCatalog.js:356` 与 `routing/route.js:46` 默认 3，后台文案硬编码「阈值: 5 次」（`HealthMonitorClient.jsx:216`）。

### 3.4 健康度与统计页「看着正常、其实全零」

`getChannelsHealthOverview` 的 24h 成功率与平均延迟聚合自 `generation_attempts`（`circuitBreaker.js:124`）——**该表恒为 0 行**，于是 `total===0` 时 `successRate` 直接返回 100。成本中心同理，且 `CostCenterClient.jsx:143` 又叠了一层 `successRate || 100`。利润中心的成本侧恒为 0，毛利率恒 ≈100%，`isMarginAlert` 永不触发。

唯一真实的遥测源 `provider_call_logs`（`recordProviderCall`，每次上游调用都写）**已经在线积累数据，但路由评分完全没用它**：`smartRouter.js:116` 用 `provider_type === 'official' ? 90 : 80` 当速度分，`:109-113` 用健康字符串凑稳定分，§8 要求的历史成功率、平均响应、429 频率、5xx 频率、当前并发、余额六项**一项都没读**。

### 3.5 状态机宽严不一致

`019` 已把 `creations_status_check` 放宽到 11 态（§11 全量），但 `lib/services/generationState.js:1-15` 只实现 5 态（queued/processing/succeeded/failed/cancelled）。前端亦不消费归一化状态：`packages/studio/src/utils/generationLifecycle.js:1-2` 直接比对 `completed/succeeded/success` 等原始供应商状态串，代理层还要 `succeeded→completed` 反向打补丁（`route.js:37-39`）。违反 §11「禁止前端直接依赖供应商状态」。

### 02 遗留：积分刻度冲突（阻断 `model_pricing` 落库）

| 证据 | 数值 |
|---|---|
| 实际扣费来源 `models_config.credits_price` | 540 行：`1`×76、`2`×138、`10`×321，其余 5 行 6/8/12/18/20；`generationCore.js:76` 直接按它冻结积分 |
| 真实台账 `credit_ledger_v2` | `TASK_RESERVE` delta = **-2**（一次生成 2 积分）；`CREDIT_GRANT` 最大 2400 |
| 套餐赠分口径 `plans_config` | Starter ¥140 → 2000 分；Basic ¥350 → 5000；Plus ¥700 → 10000；Pro ¥1400 → 20000 ⇒ **¥0.07/积分** |
| 中台种子 `model_pricing`（019，从未参与扣费） | 88 行，base_credits 10–590，均值 130.6；视频类普遍 500 |
| 聚合网关真实成本 | 540 行里 532 行 `cost_usd = 0`（未回填），019 种子示例 Kling 2.6 为 0.60 USD ≈ ¥4.3 |

矛盾：¥140 卖 2000 积分，而一次视频生成实际只收 1–2 积分（≈¥0.14），供应商侧成本以美元计。两套刻度若直接合表，要么全站价格瞬间放大 50–500 倍，要么继续沿用注定亏损的价格且 §42 的「预计消耗 1800 Credits」无法自洽。这是定价商业决策，不在技术改造权限内，因此同步器只补齐模型/渠道/路由，`model_pricing` 保持为显式缺口（`gaps.model_without_pricing`）等待裁定。

**2026-09-20 裁定（业主）**：方向按**套餐口径**重定全站价（¥0.07/积分 + 毛利下限），但**先由工程侧给出各档目标价清单，业主确认后才落库**；在此之前不得改任何用户可见价格。
因此本轮的处置是：`model_pricing` 继续保持缺口，Phase 05 的报价引擎先以服务端 `models_config.credits_price` 为唯一权威价（客户端仍不可伪造价格），目标价清单见 `docs/定价提案-积分刻度统一.md`（Phase 05 交付前置）。

**2026-09-21 复核（本节结论需修正）**：目标价清单取数后，上文「两套刻度不兼容」的判断**在全部 8 个已知成本锚点上不成立**。按 `CREDIT_VALUATION.USD_PER_CREDIT = 0.01`（= ¥0.072/积分，与套餐口径一致）计算，这 8 行的现价/成本比稳定落在 2.0×–3.3×（名义毛利 50%–70%），说明当年录成本的人用的就是套餐口径；「全站价格瞬间放大 50–500 倍」的风险不在 `credits_price` 侧，而在 `model_pricing` 的 500/590 量级种子被 Phase 05 启用为报价来源的那一天。真正的缺口是成本数据覆盖（540 行里 8 行有 `cost_usd`、`provider_cost_records` 全表 0 行）与 `cost_config.base_cost` 缺单位约定（同模型两渠道差 16×–468×）。详见 `docs/定价提案-积分刻度统一.md` §1–§3。
仍成立的结论：定价是商业决策，不在改造权限内；`model_pricing` 保持显式缺口；Phase 05 先 parity 上线。
