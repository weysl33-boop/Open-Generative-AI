## 0. 结论先行

本次审计最重要的结论**不是**登录框的样式问题，而是：

> **站点的默认（英文）路由树在整页输出中文。**
> `/pricing`、`/credits`、`/community`、`/creations` 四个页面的 `<html lang="en">`，但 `<title>`、`<h1>`、正文、按钮全部是硬编码中文；`zh-CN` / `ja-JP` / `ko-KR` / `zh-TW` / `es` 用户拿到的也是同一份中文。

## 2. P0-1 默认英文路由整页中文

### 现象（实测）

| 路由 | `html lang` | `<title>` | `<h1>` | 是否调用文案层 |
|------|-------------|-----------|--------|----------------|
| `/pricing` | `en` | `会员方案与定价 — KoyoSIM AI Studio` | `价格与套餐` | 否 |
| `/credits` | `en` | `算力资产与积分中心 — KoyoSIM AI Studio` | `我的创作资产与专属 K 币` | 否 |
| `/community` | `en` | `社区 — 探索 AI 艺术灵感与一键做同款 \| KoyoSIM AI Studio` | `把灵感变成下一次创作` | 否（二元 `isZh`） |
| `/creations` | `en` | `个人作品资产中心 — KoyoSIM AI Studio` | **无 `<h1>`** | 否（二元 `isZh`） |
| `/studio` | `en` | `Studio — koyosim` | 英文（正常） | 是 |

同一会话内的直接后果（`dialog-pricing.png` 可复核）：

- `/studio` 的登录框渲染英文（`Creator Account Login` / `Email Login` / `Sign In`）
- `/pricing`、`/credits` 的登录框渲染中文（`创作者账号登录` / `邮箱账号登录` / `安全登录`）
- 而这三页的 `htmlLang` 都是 `en`

对 SEO 与读屏软件是硬错误：`lang="en"` 的文档内容是中文，屏幕阅读器会用英文发音引擎读中文。

### 根因（源码定位）

**根因 A — metadata 与页面标题硬编码中文，且不接收 locale**

```
app/pricing/page.js:4      title: '会员方案与定价 — KoyoSIM AI Studio'
app/credits/page.js:4      title: '算力资产与积分中心 — KoyoSIM AI Studio'
app/community/page.js:4    title: '社区 — 探索 AI 艺术灵感与一键做同款 | …'
app/creations/page.js:4    title: '个人作品资产中心 — KoyoSIM AI Studio'
components/pricing/PricingClient.js:206   <StudioHeader title="价格与套餐" subtitle="专业 AI 创作工作站 · 独立订阅定价体系" />
components/credits/CreditsClient.js:218   <StudioHeader title="创作额度与专属代币" subtitle="管理 K 币、月度专属额度与算力积分" />
```

这 4 个 `*Client.js` 目录中 `getCommonCopy` 命中数为 **0** —— 即完全没接文案层。

**根因 B — 共享组件把默认语言写死为 `'zh-CN'`（与 `DEFAULT_LOCALE = 'en'` 矛盾）**

```js
// components/community/CommunityClient.js:176-178   ← 同时也是 components/creations/CreationsClient.js:268-270
const isZh = typeof document !== 'undefined'
  ? (document.cookie.match(/(?:^|;\s*)(?:NEXT_LOCALE|locale)=([^;]+)/)?.[1] || 'zh-CN').startsWith('zh')
  : true;
```

四处独立缺陷叠加：

1. `|| 'zh-CN'` —— 无 cookie 的访客（首次到达的英文用户）**恒为中文**。
2. `: true` —— **SSR 分支恒中文**，服务端 HTML 永远输出中文，客户端 hydrate 后才可能改变 → 结构上无法正确 SSR，且有 hydration 闪烁。
3. 只看 cookie，**完全忽略 URL 路径段** → 访问 `/ja-JP/…`、`/es/…` 时只要没 cookie 仍是中文。
4. `isZh` 是**二元**判断 → `zh-TW` 被当作 `zh-CN`，`ja-JP` / `ko-KR` / `es` 全部落到英文，6 个 locale 实际只有 2 种文案。

同样模式的还有：

```
components/site/StudioHeader.js:178   normalizeLocale(getLocaleFromPathname(pathname) || user?.locale || getCookieLocale() || 'zh-CN')
components/UserDropdownMenu.js:82     normalizeLocale(locale || user?.locale || getCookieLocale() || 'zh-CN')
```

全仓 `|| 'zh-CN'` 命中 **12 处**。

**根因 C — 违反仓库自身明文约定**

`lib/locales.js:14` 写着：

> `Do not add locale === 'zh'-style branches in shared components — read copy from this registry instead.`

`CommunityClient.js:176` / `CreationsClient.js:268` / `StudioHeader.js:179` / `UserDropdownMenu.js:83` 四处直接违反。

**根因 D — 路由树不完整**

```
app/[locale]/          → 只有 page.js 与 studio/[[...slug]]
app/zh/                → assistant call-api credits pricing studio subscription
app/zh-TW|ja-JP|ko-KR|es → 空（仅 [locale] 树覆盖 studio）
```

即 `/ja-JP/pricing`、`/es/credits`、任何 locale 的 `/community`、`/creations` **都还没有路由**。所以这几个页面目前只能靠 cookie 嗅探，也就是根因 B。

### 修复建议（按顺序）

1. ~~**先抽公共函数**~~ **已做**：解析器落在 `lib/locales.js` 的 `resolveClientLocale()`（显式 prop → 路径断言 → 用户偏好 → cookie → `DEFAULT_LOCALE`），4 个组件的私有 `isZh` / `getCookieLocale` 已删除。`AuthModal.js` 里那份私有 `resolveLocale()` 是重复实现，**待该文件的并发编辑方停手后再合并**（见 §2.6 末）。
2. ~~**消灭 `|| 'zh-CN'`**~~ **已做**：`DEFAULT_LOCALE` 现为唯一回落值，且服务端 locale 由 `page.js` 透传，hydration 分裂一并消除（验证见 §2.6）。
3. **`isZh` 升级为 6 路 `copy` 对象**：仿 `authModal` 命名空间，为 `pricing` / `credits` / `community` / `creations` 各建命名空间，`getCommonCopy(locale)` 取文案；`metadata` 改为 `generateMetadata({ params })`。
4. **补路由树**：`app/[locale]/[...slug]` 覆盖 4 页，或明确宣布"这 4 页暂不做多语言"并从语言菜单里禁用它们，不要给半个承诺。（未做）
5. **加闸**：`scripts/validate-i18n.mjs --strict` 目前只校验 `messages/*.json` 键位对齐，无法发现"组件根本没读 messages"。建议新增一条静态门禁：`components/{pricing,credits,community,creations}/**` 中出现裸 CJK 字面量即 FAIL。（未做）

### 2.6 已落地：解析层修复（1、2 两步）

|------|------|

## 3. P0-2 登录对话框可达性缺陷（线上旧实现）

实测 4 个入口（`/studio`、`/pricing`、`/credits`、390px 移动端），结果**完全一致**：

| 检查项 | 契约要求 | 线上实测 | 判定 |
|--------|----------|----------|------|
| 对话框可访问名称 | `aria-labelledby` 指向标题 | `labelledby: null`、`labelledbyResolves: false` | **FAIL** |
| 描述关联 | `aria-describedby` | `describedby: null` | **FAIL** |
| 焦点陷阱 | Tab 循环锁在面板内 | `focusTrap: "ESCAPED at step 0"`（`/studio`）<br>`"ESCAPED at step 12"`（`/pricing`、`/credits`） | **FAIL** |
| 打开后焦点位置 | 移入面板 | `activeInDialog: false`（焦点停在背景表头按钮 `button.flex items-center gap-1 rounded-full bg-cyan-`） | **FAIL** |
| ESC 关闭 | 必须 | `escCloses: false` | **FAIL** |
| 点遮罩关闭 | 必须 | `overlayClickCloses: false` | **FAIL** |
| 背景滚动锁 | `body { overflow: hidden }` | `bodyOverflow: "visible"`、`htmlOverflow: "visible"` | **FAIL** |
| 表单控件可访问名 | `<label for>` 或 `aria-label` | `labels: []`，两个 `<input>` 均 `id: null`、`labelled: false`、`aria: null` | **FAIL** |
| 邮箱自动填充 | `autocomplete="email"` / `"current-password"` | `ac: null` | **FAIL** |
| 错误播报 | `role="alert"` + `aria-invalid` | `roles: { tablist: 0, tab: 0, alert: 0, radiogroup: 0, ariaErrorFields: 0 }` | **FAIL** |
| 模式语义 | `role="dialog" aria-modal` | 有 —— 但 `role="dialog"` 挂在**遮罩本身**（`div.fixed.inset-0.z-[220].bg-black/80`）而非面板 | 结构错误 |

综合判定：**键盘与读屏用户无法使用该登录框。** 焦点从未进入面板即被背景元素接走，ESC 与遮罩点击都无法退出，输入框对读屏只报 "edit text"。

补充：`aria-label="关闭"` 出现在英文对话框上（`/studio`，`htmlLang="en"`）—— 即根因 B 的又一处外溢。

### 已落地的修复（未部署）

即：**主转化按钮上的白字落在白底上，肉眼不可见。**

### 根因

```jsx
// components/creations/CreationsClient.js:305
<Button className="h-10 px-6 rounded-full bg-white text-black font-semibold …">
// components/creations/CreationsClient.js:407
<Button className="rounded-full bg-white hover:bg-white/90 text-black px-6 py-2.5 …">
// components/credits/CreditsClient.js:633
<Button className="rounded-xl bg-white text-black font-semibold text-xs px-5 …">
```

两个问题叠加：

1. **`cn` 是纯拼接器，不是 tailwind-merge**（仓库文档中的 NO-CONFLICT INVARIANT）。设计系统 `Button` 基类带 `text-ink`（近白 `#ededf0`），调用点又追加 `text-black` —— 同一个 `color` 属性出现两个工具类，**胜负由编译后 CSS 的源码顺序决定，与 class 字符串顺序无关**。实测 `text-ink` 赢 → 白字白底。这不是偶发，是不确定行为，换一次 Tailwind 排序就可能反向。
2. **`bg-white` / `text-black` 本身就是 off-token。** 契约早已定义了这对语义：`app/globals.css:22 --bg-inverse: #f4f5f7`（注释：*light chips on dark surfaces*）、`app/globals.css:40 --text-inverse: #0a0b0d`，映射在 `tailwind.config.js:30/41`。写 `bg-white text-black` 绕开了它们，同时把纯白纯黑引入暗色主题（刺眼、且违反 ratchet）。

### 修复建议

- 三处改 `bg-surface-inverse text-inverse`，删掉 `bg-white` / `text-black`。
- **更根本**：设计系统缺一枚反向按钮。`packages/studio/src/ui/tokens.js:114` 的 `BUTTON_VARIANTS` 只有 `primary / secondary / tertiary / outline / danger`。新增 `inverse: ['bg-surface-inverse text-inverse border-transparent', 'hover:bg-surface-inverse-hover …']`，调用点写 `variant="inverse"`，让冲突在结构上不可能发生。
- **加闸**：`ui-token-guard.mjs` 目前只能按文件计数，抓不到"同一字符串里同一属性出现两个工具类"。建议新增 `conflicting-utility` 规则，检测同一 class 字符串中同属性前缀重复（`text-*`×2、`bg-*`×2、`rounded-*`×2），这类缺陷只在运行时暴露，值得一个静态门禁。
