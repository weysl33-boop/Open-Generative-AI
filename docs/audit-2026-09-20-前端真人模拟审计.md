## 一、已确认问题（Round 1）

### A-01 [P0] 第三方登录错误回跳指向内网地址 `https://localhost:3100/account`
- 复现：
  - `curl -sSI https://www.koyosim.com/login` → `302 location: https://localhost:3100/account`
  - `GET https://www.koyosim.com/api/auth/oauth/github` → `307 location: https://localhost:3100/account?auth_error=不支持的登录方式`
  - `GET https://www.koyosim.com/api/auth/oauth/discord` → 同上
- 根因：nginx `proxy_pass` 到 `127.0.0.1:3100` 且未回传对外 Host，线上旧产物用 `new URL(path, request.url)` 拼绝对地址 → 得到内网 origin。
  - 旧产物证据：`release-staging/app/api/auth/oauth/[provider]/route.js:24` 仍是 `NextResponse.redirect(new URL(..., request.url))`
  - 工作树已修：`app/login/route.js`、`app/api/auth/oauth/[provider]/route.js:27-30`、`app/auth/[provider]/callback/route.js:10`、`app/auth/tiktok/route.js:6`（commit `17527c4`）
- 影响：用户点击登录/不支持的登录方式后被送到打不开的本机地址，登录链路断裂。
- 修复状态：**代码已修但未部署**。部署需用户批准（工作树 573 个脏文件、含 5 个并发会话改动，不可盲发）。

### A-02 [P1] 登录方式清单与后端能力不一致
- 后端 `lib/oauth.js:6-31` 仅注册 `google` / `x` / `tiktok`；`getOAuthProvider()` 对 `github`、`discord` 返回 null → 「不支持的登录方式」。
- 待确认项：登录弹窗 UI 是否展示 GitHub / Discord 入口（若展示即 FAKE FEATURE）。

### A-03 [P1] 未登录状态下 `/studio` 首页即产生 401 与未捕获 console error

### A-04 [P1] `/studio/design-agent` 丢失左侧导航与页面壳

### A-09 [P0] `react-konva@19.3.0` 与 Next 内置 React 版本冲突，会把全部 17 个 `/studio/*` 菜单打成 500
- 现象（工作树，非生产）：本地 dev 下 `/studio` 与**所有**子路由 500，SSR 阶段抛
  `Error: react-konva requires React 19.3 or later within React 19.`
- 传播链（一个叶子组件拖垮整个导航）：
  `node_modules/react-konva/es/ReactKonvaCore.js:11-13`
  ← `packages/Open-AI-Design-Agent/packages/design-agent/src/CanvasArea.jsx:10`
  ← `.../design-agent/src/index.js:8`
  ← `packages/studio/src/components/DesignAgentStudio.jsx:9`
  ← `packages/studio/src/index.js:128`
  ← `components/StandaloneShell.js:11`
- 根因（已逐层核实）：`react-konva` 的守卫是模块初始化时的硬判断
  `const [major, minor] = React.version.split('.').map(Number); if (major !== 19 || minor < 3) throw`。
  而 App Router 的 SSR 拿到的 `react` 不是 `node_modules/react`（那里确实是 19.3.0），而是 Next 自带的
  `next/dist/compiled/react`，其版本串为 **`19.2.0-canary-0bdb9206-20250818`**（`next@15.5.25`）。
  `minor = 2 < 3` → 必然抛错。`node_modules` 内不存在第二份 react 副本（`packages/Open-AI-Design-Agent/node_modules/react` 也是 19.3.0），所以这不是重复安装问题，而是 **Next 版本与 react-konva 版本约束不相容**。
- 加重因素：`design-agent` 的 `package.json` 写 `main: dist/index.js`，但本次报错栈走的是 `src/*.jsx`——因为 `next.config.mjs:7` 的 `transpilePackages: [..., 'design-agent']` 会优先按源码解析；而未提交的 `next.config.js` 遮蔽了 `.mjs`（见项目记忆），两条配置线哪个生效取决于当时磁盘上是谁的 config，属于隐蔽的构建不确定性。
- 影响：
  1. 本地 dev/`next build` 产物不可用 → §29「改完代码再跑浏览器」和登录态回归全部阻塞；
  2. `react-konva ^19.0.0` 是 design-agent 的**直接依赖**且 `package.json` 未锁 `19.2`，因此一次 `npm install` 解析到 19.3.x 就会复现——即下一次部署若沿用当前 lock，**生产 17 个菜单全 500**。
- 与生产的关系：生产当前不报此错（本轮 `sweep-links` 中 17/17 `/studio/*` 返回 200），因为线上跑的是更早的 `release-staging` 产物；也就是说这是一个**尚未引爆的部署期 P0**，而不是当前用户可见故障。
- 修复建议（二选一，都需要改依赖，属于影响 5 个并发会话共享 `node_modules` 的高半径操作，本会话**不擅自执行**）：
  - 把 `react-konva` 锁到 `19.2.x`（design-agent 声明的是 `^19.0.0`，19.2 合法）；或
  - 升级 `next` 到内置 React ≥ 19.3 的版本，再统一复核 `peerDependencies`。
  - 反例（§28 禁止）：把 design-agent 从导航里摘掉、或给 `DesignAgentStudio` 包 `ssr:false` 动态导入——`ssr:false` 只把抛错从服务端挪到客户端，守卫在浏览器里同样失败，等于掩盖而不是修复。
- 修复状态：**未修复（阻塞项）**，需用户确认依赖变更后执行。

### 探针方法论（下轮必须沿用，避免再次误判）
1. 必须 `page.on('dialog')` 并 `dismiss()`，否则 Playwright 自动吞掉 alert，把有效校验误判为死按钮。

### 二十二·四 A-26 [P2] 生成失败的可见结果：只有 `Failed to load.`，无原因、无重试（§17）

### 二十七·二 §26 根因定位（全部在 `components/credits/CreditsClient.js`）

1. `loadLedger()` 只有 `catch { // 容错降级 }`，**没有 error state**；渲染层写的是 `ledgerLoading ? … : filteredLedger.length === 0 ? '暂无资产流水记录'` —— 失败与空被折叠成同一个空态（→ **A-35**）。
2. `handleCheckIn()` **无在途锁**（既不看 loading 也不看 `disabled`），所以 3 连点发 2 个 POST；失败分支 `setMessage(data.error || …)` 直接把后端兜底文案原样上屏（→ **A-36**）。
3. `app/api/financial/credits/checkin/route.js` 把"今日已签到"与真异常一起 `catch-all → publicErrorMessage(…, t('common.failed'))` 折叠成 **400 + 英文 `Failed`**；**API 错误响应不参与 locale**（→ **A-37**）。
4. `handleClaimDailyKCoin()` 的失败分支写 `setMessage(data.error || '今日登录奖励已领取'); setDailyClaimed(true);` —— **任何非 2xx（含 500/401）都会永久锁死当天按钮**（→ **A-38**；本轮生产腿未观测到，当时按钮已领，属代码定位的潜伏缺陷，如实标注）。

### 1. A-42 [P3] Rename：可重复提交 + 空名静默

**发现路径**：跑 A-40/A-41 的回归时顺手点到 My Workflows 卡片的 ⋯ → Rename（这个入口只在 `activeTab === 'my-workflows'` 下渲染，所以前几轮一直没覆盖）。

**根因（§26）**：`WorkflowStudio.jsx` 的 `handleRenameWorkflow`（`:340-359`）里，`if (!renamingWorkflow || !newWorkflowName.trim()) return;` 之后的 `await updateWorkflowName(...)` 外**没有任何在飞标记**，而 `Save Name` 按钮（`:1052`）**没有 `disabled`**。后果两条：
- 慢网下连点 N 次 = N 个 `POST /api/workflow/update-name/<id>`，同一个工作流被写 N 次（§16「用户可以重复 Submit」）。
- 输入框清空后按钮**仍然可点**，点下去只走那条 `return`，没有任何提示、没有 loading、没有错误 —— 用户视角就是"这个按钮坏了"（§11「按钮无响应」+ §17「错误状态缺失」）。

**修复（§27，工作树未提交）**：新增 `renaming` state（`:174`）+ `renamingRef`（`:175`）。`ref` 而不是只用 state，是因为 state 在同一批事件里读到的还是旧值；`:343-344` `if (renamingRef.current) return; renamingRef.current = true;`，`:359` 在 `finally` 里释放。按钮改 `disabled={!newWorkflowName.trim() || renaming}`（`:1052`），文案 `Saving...` / `Save Name` 交替（`:1055`）。**空名不是静默 return，而是按钮压根不可点且 `cursor:not-allowed`** —— 这是修法里唯一有主张的选择：不用 toast 补提示（§28 禁止用提示掩盖交互缺陷）。

### 2. A-43 [P3] Delete：`isDeletingId` 写了但没人读，等于没有保护

**根因（§26）**：`handleDeleteWorkflow`（`:324-337`）确实 `setIsDeletingId(wfId)`（`:326`）、`finally` 里 `setIsDeletingId(null)`（`:334`）—— 但 `isDeletingId` 这个 state **在整个组件里只出现在声明行 `:176`**（`grep -n "DeletingId"` 只有 3 行：声明 + 两次写入）。也就是说这个"在飞状态"从不参与渲染，Delete 菜单项（`:94-101`）既没有 `disabled` 也没有 spinner。修前依据是这条静态事实（不是浏览器观测），后果：第一发 `DELETE` 还在飞时，卡片仍在列表里（本地 `filter` 只在成功后执行），用户 ⋯ → Delete → 确认 → **第二个 DELETE 打到同一个 id**，厂商侧此时多半返回 404/409/500 → 走 `catch` → `alert("Failed to delete workflow")`（`:332`）——**删除其实成功了，UI 却弹"删除失败"**。这是 §10「显示成功/失败但与实际不符」的反向形态，也是 §16「按钮已执行但没有 Disabled」的教科书样本。

**修复（§27）**：把那个死状态接上，并且刻意**不用**"只禁用当前行"的做法 —— 若只有 A 行禁用、handler 里再写 `if (isDeletingId) return;`，那么 B 行按钮**看着能点、点了静默无事**，等于亲手制造一个新的 §11 无响应按钮（这正是 A-42 要修的病）。所以 `WorkflowCard` 收一个 `deletingId` prop：`disabled={deletingId !== null}`（任一行在飞 → 全行禁用），`{deletingId === workflow.id ? "Deleting..." : "Delete"}`（只有真正在删的那行换文案），并补 `disabled:opacity-50 disabled:cursor-not-allowed disabled:hover:bg-transparent`。`confirm()` 阻塞式弹窗保留不动（它不属于本条，英文硬编码归 A-18）。
